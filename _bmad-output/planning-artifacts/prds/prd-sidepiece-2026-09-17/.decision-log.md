### MV3 capability research folded in

Digest received and reconciled into addendum §C (operative) and §D (what changed).
Five corrections to the first draft:

1. **Panel document persists across tab switches.** Draft assumed per-tab
   `setOptions` overrides; research showed a global panel document survives tab
   switching and per-tab overrides carry a drift failure mode. Relaxed FR-8's
   persistence burden — state only needs to survive the panel *closing*.
2. **SSE vs WebSocket in the service worker.** WebSocket resets the idle timer;
   EventSource has no documented equivalent. Sharpens the "streams live in the
   panel document" rule and shapes FR-7's closed-panel reconciliation.
3. **Host permission scope became a real decision.** A narrow match avoids the
   permission warning entirely — but reintroduces the origin coupling that killed
   the Traefik model. Resolved in PRD §5 in favour of the broad match, valid only
   while the extension stays personally loaded. New assumption, indexed.
4. **Private Network Access.** Absent from the draft. Now a cross-cutting NFR
   plus §12 Q7, because it is the only identified failure mode that can break a
   working install with no change on our side. Mitigation is unconditional so it
   does not block; verification is empirical, not documentary.
5. **The gesture constraint fails silently.** `sidePanel.open()` must be the
   first synchronous call in the handler; an await first no-ops with no error.
   Worth knowing before it is debugged as an intermittent heisenbug.

Also added: SPA navigation needs explicit history observation (a declarative
content script alone does not satisfy FR-1); `captureVisibleTab` is rate-limited
and full-page capture costs the `debugger` permission; selector-generation
library options and their shared failure modes; four prior-art entries, of which
Vercel Toolbar validates the premise and Sourcegraph is the cautionary tale.

Four items moved from §13 Assumptions to a "verified, no longer assumptions"

### Precision fix: host match scope != SPA re-injection

A second research pass caught imprecise wording in addendum §C. The draft said a
content script "fires automatically on every navigation" and folded the SPA
problem into the host-match bullet. Both wrong in the same way: a content script
injects once per *document load*, and a history-API transition never unloads the
document, so widening the match pattern does nothing for it — match scope governs
*where* a script may inject, not *when* it re-injects.

Now two separate bullets with separate mechanisms. Recommended SPA default is a
`MutationObserver` on `<head>` in the already-injected script — cheapest, no extra
permission — with `history.pushState`/`replaceState` patching as the alternative
(`popstate` alone is insufficient; it does not fire on a `pushState` call) and
`chrome.webNavigation.onHistoryStateUpdated` reserved for when the service worker
itself needs the signal.

Also named the concrete follow-the-tab mechanism: single global panel document +
service worker listening on `tabs.onActivated`/`tabs.onUpdated`, messaging that
document to re-render. Per-tab `setOptions` is for a different product shape
entirely ("different panel per tab, or none on some tabs").

No FR text changed — PRD FR-1 already required explicit history observation.
